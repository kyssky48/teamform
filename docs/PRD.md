# PRD: 팀 편성 웹 앱 (teamform)

중간 과제 공고(10/16)를 바탕으로 쓴 설계 문서. 공고와 이 문서가 다르면 공고가 우선한다.
"공고 x.y절"은 공고의 절 번호다.

## 1. 목적과 배경

- 수강생(가상 학생)이 팀 프로젝트 팀을 스스로 편성하고, 남은 학생은 AI가 배정하되 앱이 규칙으로 검사하는 웹 앱
- 채점은 자동 채점 프로그램이 배포한 앱 화면을 Streamlit `key`로 찾아 조작해서 한다. 그래서 **화면 key와 결과 안내의 첫 단어가 정확해야 한다**는 점이 기능만큼 중요하다
- 마감: 11/2(월) 23:59. 채점: 11/3~11/4. 이 기간에 DB가 일시정지되면 시나리오 점수 0점

## 2. 목표 / 하지 않을 것 / 실패로 보는 것

**목표**
- 공고 3장의 7개 기능을 모두 **어려운 해결**로 만든다
- 공개하지 않은 채점 시나리오(학생 8~16명, 팀 3~4개)에서 결과 안내의 첫 단어가 기대 결과와 같다
- 부록 연습용 시나리오 3개를 자동 테스트로 재현해 통과한다

**하지 않을 것**
- 구글 로그인(`st.login`), 회원 가입, 비밀번호 변경
- 학생의 역할 수정, 팀 이름 변경, 마감 취소
- 예쁜 디자인. 화면은 Streamlit 기본 요소로 단순하게 둔다

**실패로 보는 것** (동작해도 감점되거나 0점이 되는 것)
- 2.7절 key가 표와 다름 (-5)
- 키나 관리자 비밀번호가 코드·커밋 기록에 들어감, 화면에 출력됨 (-3)
- 연습용 시나리오의 학생 이름이나 순서에 맞춘 코드 (그 시나리오 0점)
- AI 배정이 10분을 넘김
- 채점 기간에 Supabase 일시정지

## 3. 기술 구성 (공고가 정함)

| 항목 | 내용 |
|---|---|
| 앱 | Python 3.12, Streamlit, 앱 파일 `streamlit_app.py` |
| DB | Supabase(Postgres). 테이블 이름은 모두 `tf_`로 시작. 생성 SQL은 `schema.sql` |
| AI | OpenRouter 텍스트 생성 모델 3개(1·2·3차). `openrouter/free` 금지 |
| 배포 | Streamlit Community Cloud, 비공개 GitHub 저장소의 `main` 브랜치 |
| 비밀 값 | `OPENROUTER_API_KEY`, `DATABASE_URL`, `ADMIN_PASSWORD`. 로컬은 `.env`, 배포는 Streamlit Secrets |
| 비밀번호 | bcrypt 해시로 저장 |

**제가 정한 것**
- DB 드라이버는 `psycopg`(3). 연결은 `st.cache_resource`로 한 번만 만들고 다시 쓴다(공고 4.2절)
- `DATABASE_URL`은 Supabase의 **Session pooler** 주소를 쓴다. Direct connection 주소는 IPv6 전용이라 Streamlit Cloud에서 연결이 안 될 수 있다
- 비밀 값은 `st.secrets`에 있으면 그것을, 없으면 `.env`를 읽는다. 값이 있는지 확인할 때는 "있음/없음"만 출력한다

## 4. 사용자와 화면

### 4.1 로그인 (모든 사용자)
- 학번(`login_student_no`), 비밀번호(`login_password`), 로그인 단추(`login_submit`)
- 학번 `admin`은 관리자. 앱이 시작할 때 `ADMIN_PASSWORD`로 관리자 계정을 만들거나 비밀번호 해시를 갱신한다. 명단을 다시 올려도 관리자 계정은 남는다
- 학생 비밀번호는 모두 `1234`
- 비밀번호가 틀리면 로그인되지 않는다. 학번만으로는 들어갈 수 없다
- 로그인한 사람은 `whoami` 컨테이너에 이름으로 보인다
- 채점 프로그램은 학생마다 브라우저를 따로 연다. 로그인 상태는 `st.session_state`에 두므로 브라우저마다 따로 유지된다
- 화면을 그릴 때마다 로그인한 학번이 DB에 아직 있는지 확인한다. 관리자가 명단을 다시 올려 그 학생이 사라졌으면 로그인 화면으로 돌아간다(제가 정한 것)

### 4.2 학생 화면
- 팀마다 `team_{번호}` 컨테이너. 팀원의 이름, 주 역할, 보조 역할을 보여 준다. 내 팀에는 "내 팀" 표시, 팀이 없으면 "아직 팀이 없음"
- 팀마다 지원 단추 `apply_{번호}`
  - 이미 팀이 있음, 결과를 기다리는 지원이 있음, 모집 마감 → 단추를 **비활성화**(공고 2.8절)
  - 그 밖의 막힘(꽉 참, 같은 주 역할, 필수 역할 자리)은 단추를 누르면 `result`에 "막힘: 이유"를 보여 준다
- 내 팀에 들어온 대기 중인 지원마다 찬성 `vote_yes_{지원자 학번}`, 거부 `vote_no_{지원자 학번}`
  - 이미 투표했으면 두 단추를 비활성화하고 "내 투표: 찬성"처럼 보여 준다
- 단추를 누른 결과는 `result` 컨테이너에 "승인/대기/거절/막힘"으로 시작하는 한 줄로 보여 준다
  - 지원 단추: 그 지원의 결과. 빈 팀이면 "승인", 팀원이 있으면 "대기", 규칙에 걸리면 "막힘: …"
  - 찬성·거부 단추: 그 지원의 지금 상태(승인, 대기, 거절)

### 4.3 관리자 화면
- 명단 CSV(`admin_roster_file`), 팀 수(`admin_team_count`), 처음 상태 만들기(`admin_start`)
- 모집 마감(`admin_close`), 팀이 없는 학생(`unassigned`, 이름이 보임)
- AI 배정(`admin_assign`), 진행 안내(`assign_status`), 배정안 확정(`admin_confirm`)
- 팀 현황(`team_{번호}`)도 학생 화면과 같은 꼴로 보여 준다
- 관리자 단추의 `result`도 "승인: …" 또는 "막힘: …"으로 시작한다. 예: "승인: 모집을 마감함", "막힘: 아직 마감하지 않음"
- 학생 계정으로는 관리자 화면과 관리자 동작에 접근할 수 없다. 화면을 숨기는 것뿐 아니라 동작 함수에서도 관리자인지 다시 확인한다

### 4.4 다른 사람의 변경 보기 (어려운 해결)
- 팀 목록, 투표 단추, `unassigned`를 `st.fragment(run_every=3초)` 안에 둬서 바뀐 부분만 다시 그린다(공고: 5초 이하)
- `refresh` 단추는 두지 않는다(쉬운 해결 전용)
- **위험**: fragment 안의 단추를 누르면 fragment만 다시 실행되므로, `result`도 같은 fragment 안에 두거나 결과 문구를 `session_state`에 저장해 다시 그려야 한다. 구현 초기에 실제 브라우저로 key를 찾는 시험(아래 10절)으로 확인한다

## 6. 팀 규칙 (공고 2.3절)

- 팀 인원: 확정한 팀 구성에서 모든 팀이 2~4명. 빈 팀 없음
- 주 역할 중복 금지: 같은 주 역할 학생이 한 팀에 2명 이상이면 안 됨
- 필수 포함 역할: 모든 팀에 기획자와 웹 프로그래머를 **서로 다른 학생**이 맡아야 함. 주 역할이나 보조 역할로 맡을 수 있음
  - 판정은 "기획자 자리"와 "웹 프로그래머 자리"를 팀원에게 겹치지 않게 짝짓는 문제로 푼다. 팀원이 4명 이하라 모든 경우를 따져도 된다
- **필수 역할 자리 계산**(공고 3장): 지원자가 들어간 뒤 남는 자리 수(4 − 인원)가 아직 채우지 못한 필수 역할 수보다 적으면 막는다
  - 예: 테스터와 발표자만 있는 팀(2명)에 보고서 작성자가 지원 → 들어가면 3명, 남는 자리 1, 못 채운 필수 역할 2 → 막힘
  - 예: 기획자이면서 보조로 웹 프로그래머인 학생 혼자 있는 팀은 필수 역할 1개만 채운 것

## 7. 지원과 투표 (공고 2.4절)

### 7.1 지원 단추를 눌렀을 때 검사 순서
아래 중 하나라도 걸리면 접수하지 않고 "막힘: 이유"를 보여 준다. DB에 기록하지 않는다.
1. 모집이 마감됨
2. 이미 팀이 있음
3. 결과를 기다리는 지원이 있음
4. 팀이 꽉 참(4명)
5. 같은 주 역할의 팀원이 있음
6. 필수 포함 역할을 맡을 학생의 자리가 모자람

통과하면:
- 팀이 비어 있으면 바로 승인하고 팀원으로 넣는다 → "승인"
- 팀원이 있으면 대기로 접수한다 → "대기"

### 7.2 투표
- 투표할 사람은 **투표하는 때의 팀원**이다. 지원한 뒤에 새로 들어온 팀원도 투표해야 한다
- 한 번 투표하면 바꿀 수 없다
- 한 명이라도 거부하면 다른 사람을 기다리지 않고 바로 거절
- 그때의 팀원 모두가 찬성하면 **승인 직전 검사**(어려운 해결)를 한다: 정원, 주 역할 중복, 필수 역할 자리를 7.1절 4~6번으로 다시 검사
  - 통과하면 승인하고 팀원으로 넣는다
  - 걸리면 거절하고 `reason`에 이유를 남긴다(예: "승인 직전 검사: 같은 주 역할의 팀원이 있음")
- 처리 순서는 지원한 순서가 아니라 투표가 끝난 순서다. 승인 전에는 다른 대기 지원을 미리 거절하지 않는다
- 투표 결과 안내: 투표를 반영한 뒤 그 지원의 지금 상태로 "승인", "대기", "거절: 이유"

### 7.3 동시에 들어가는 경우 (어려운 해결)
- 팀원을 넣을 때 빈 `slot_no`를 골라 `insert`한다. 같은 자리에 두 명이 동시에 들어가면 (`team_id`, `slot_no`) 기본 키 위반으로 나중 것이 실패하고, 그 지원은 거절한다
- 투표·승인 처리는 한 트랜잭션에서 하고, 그 팀 행을 `select … for update`로 잠가 같은 팀의 동시 처리를 줄 세운다

## 8. 마감과 배정 (공고 2.5절)

### 8.1 모집 마감
- 한 트랜잭션에서: `closed=true`, 대기 지원을 모두 거절(이유 "모집 마감"), 1명뿐인 팀의 학생을 팀에서 뺀다
- 이후 지원과 투표는 막힘
- 관리자 화면 `unassigned`에 팀이 없는 학생의 이름이 보인다

### 8.2 AI 배정 (`admin_assign`)
1. 마감 전이면 "막힘: 아직 마감하지 않음"
2. 먼저 앱이 **모든 경우를 따져** 규칙을 지키는 배정이 있는지 본다(8.4절). 없으면 AI를 부르지 않고 `assign_status`에 "규칙을 지키는 배정이 없음"과 이유를 보여 준다
3. 있으면 1차 → 2차 → 3차 모델 순으로 부른다. 모델마다:
   - `assign_status`에 "1차 모델(모델 이름) 응답을 기다리는 중"을 보여 준다(어려운 해결)
   - 요청을 보낸 때부터 응답을 다 받을 때까지 **전체 120초**를 잰다(어려운 해결). 응답을 스트리밍으로 받으면서 마감 시각을 넘기면 끊는다
   - 실패 조건: 120초 초과, HTTP 오류(429 포함), 빈 응답, JSON 해석 실패, 8.3절 검사 불통과
   - 성공·실패를 `tf_ai_logs`에 남긴다
4. 3차까지 실패하면 8.4절의 앱 자체 배정 결과를 쓴다(어려운 해결)
5. 검사를 통과한 배정안만 관리자에게 보여 준다: 학생 이름, 역할, 배정된 팀, 그리고 어느 모델(또는 앱)이 만들었는지
6. 배정안은 `tf_settings.pending_plan`에 저장해 둔다. 화면이 다시 그려져도 사라지지 않게 하기 위함
7. 최악의 경우 걸리는 시간은 120초 × 3 = 6분으로, 10분 제한 안이다

**AI에 보내는 내용**: 지금의 팀 구성(팀원과 역할), 팀이 없는 학생과 역할, 공고 2.3절 규칙, 이미 팀에 있는 학생은 옮기지 않는다는 조건, 답의 JSON 형식(`{"assignments":[{"student_no":"…","team":1}]}`)
**요청 옵션**: reasoning effort `low`, `max_tokens`는 넉넉히(공고 4.3절)

### 8.3 배정안 검사 (공고 2.5절 4항의 다섯 가지)
1. 팀이 없는 학생이 빠짐없이 배정됨
2. 한 학생은 한 팀에만 배정됨 (팀이 없는 학생만 배정, 이미 팀에 있는 학생은 옮기지 않음)
3. 모든 팀이 2~4명
4. 팀 안에서 주 역할 중복 없음
5. 필수 포함 역할 충족

검사에 실패하면 어느 항목에서 걸렸는지(예: "팀2에 웹 프로그래머가 없음")를 로그에 남긴다.

### 8.4 앱 자체 배정 (모든 경우를 따짐)
- 팀이 없는 학생은 8명 이하, 팀은 3~4개(공고 6.2절)라 경우의 수가 최대 4⁸ = 65,536이다. 학생을 한 명씩 팀에 넣으며, 정원이나 주 역할 중복에 걸리면 그 가지를 바로 버리는 방식으로 끝까지 찾는다
- 배정이 하나도 없으면 이유를 만든다. 예:
  - "팀3에 웹 프로그래머를 맡을 학생이 없음"(그 팀의 빈자리와 남은 학생으로 필수 역할을 채울 수 없음)
  - "팀이 없는 학생 수가 남은 자리보다 많음"
  - "빈 팀을 2명 이상으로 채울 학생이 모자람"
- 이유는 팀마다 따로 따져 찾을 수 있는 것을 먼저 보여 주고, 팀끼리 얽혀서 안 되는 경우는 "팀 사이에 학생을 나눌 방법이 없음"으로 보여 준다

### 8.5 확정 (`admin_confirm`)
- 확정 직전에 `pending_plan`을 8.3절로 한 번 더 검사하고, 통과하면 한 트랜잭션에서 `tf_members`에 넣는다 → "승인: 배정을 확정함"
- 배정안이 없으면 "막힘: 배정안이 없음"
- 확정한 팀 구성은 DB에 남아, 새 브라우저로 열어도 보인다

## 9. 명단 올리기 (공고 2.6절)

- CSV는 `utf-8-sig`로 읽는다(BOM 있어도 됨). 열: `student_no,name,main_role,sub_roles`
- 칸마다 앞뒤 공백을 지우고, 역할 이름 안의 겹친 공백은 하나로 줄인다(예: `웹  프로그래머` → `웹 프로그래머`)
- `sub_roles`는 `;`로 나누고, 비어 있으면 보조 역할 없음
- 역할이 6개 밖이거나 열 수가 틀리거나 학번이 겹치면 아무것도 바꾸지 않고 "막힘: n번째 줄 …"
- 팀 수는 1 이상. 팀1, 팀2, …를 만든다
- 학생 비밀번호 `1234`의 bcrypt 해시는 한 번만 만들어 모든 학생에게 넣는다(학생 16명을 따로 해시하면 수 초가 걸려서. 제가 정한 것)

## 10. 검증 계획

- **규칙 단위 테스트**(pytest, TDD): 지원 검사 6가지, 필수 역할 자리 계산, 짝짓기, 배정안 검사 5가지, 자체 배정, 이유 만들기, CSV 읽기
- **시나리오 테스트**: 앱의 동작 함수(지원, 투표, 마감, 배정, 확정)를 DB 대신 메모리 저장소로 돌려 부록 시나리오 3개의 단계별 기대 결과를 확인한다. 이 테스트는 시나리오 데이터를 테스트 쪽에만 두고, 앱 코드에는 학생 이름이나 순서를 넣지 않는다
- 연습용과 다른 임의의 명단(학생 8~16명, 팀 3~4개)으로 자체 배정과 검사를 무작위 시험한다. 채점 시나리오가 연습용과 다르기 때문
- **화면 key 시험**: 로컬에서 앱을 띄우고 브라우저 자동화로 2.7절 key를 찾아 쉬움 시나리오를 처음부터 끝까지 눌러 본다(채점 프로그램을 흉내 냄)
- **AI 실패 처리**: 가짜 모델 응답(지연, 429, 빈 응답, 규칙 위반)으로 다음 모델로 넘어가는지 테스트한다. 실제 OpenRouter 호출은 하루 50회 한도가 있어 아껴 쓴다
- 배포 뒤 시크릿 창으로 연습용 시나리오 3개를 직접 해 본다
